# SRRIS Admin Service Operations

Use this skill for work under `/admin`, request processing, feedback management, the feedback builder, or generated PDFs.

## Admin conventions

- Admin routes require authentication and the `superadmin` role. Keep module pages inside the existing admin route group.
- Reuse `AdminShell`, index controls, pagination, confirmation dialogs, and feedback modals before making page-specific alternatives.
- Admin lists fetch a filtered, paginated server result. Preserve search, entries, and status or role filters when extending an index.
- Keep reusable browser behavior in `resources/js/utils`. Use `useQueryTab` when an admin workflow tab must survive reloads and shared URLs.

## R&D and feedback workflow

- The R&D form transitions a request to `for_payment`; payment verification transitions it to `awaiting_feedback`; a submitted feedback response transitions it to `completed`.
- Each stage's redirect appends `?tab=<next-tab>` so the admin lands on the next relevant tab of the next page automatically; requests-list action links do the same. Use `useQueryTab` on any tabbed admin page, and keep new stage transitions consistent with this pattern.
- Feedback links are time-limited public URLs generated by `FeedbackLinkService`. Treat generated and submitted links as request data, and use the existing link and response services instead of inventing a separate token flow. A reminder action that emails a link (payment or feedback) should generate/reuse the link and interpolate its real URL into the template — never hardcode a static or external link in a `FormTemplate` body.
- A completed R&D request keeps the same tabbed feedback page reachable (via a "More Info" action) for read-only review; gate any stage-specific action button (send reminder, generate link, etc.) behind the request's `status_value` so completed requests only show past state, not more actions.
- Builder dimensions and statements have persisted positions. Preserve drag-and-drop ordering and the accordion’s local-storage state.
- A final, state-changing submit (creating the R&D form, verifying payment, submitting public feedback) confirms first: reuse `ConfirmActionModal` for a plain yes/no confirmation, or `CodeConfirmationModal` when a four-digit code should also be required.

## PDF output

- Use TCPDF for PDFs. Do not use DOMPDF or browser `window.print()` for generated documents.
- Use `FeedbackPdfService` as the model for structured, native TCPDF drawing when visual fidelity matters. Draw bounded sections explicitly and move unsplittable blocks to a new page when they do not fit.
- Keep the generated feedback PDF landscape so rating columns remain readable without scrolling or compression.

Read [Admin Operations](../../../docs/admin-operations.md) for module responsibilities, route behavior, and the PDF rendering details.
